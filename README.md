# 卡丘战绩档案 - QQ机器人插件开发文档

## 一、 插件简介
本插件用于在QQ群聊中快速查询《卡拉彼丘》（Strinova）的玩家战绩、对局详情及排行榜数据。

*   **开发框架**：基于 Java 21 的 Kokona（https://github.com/szzz666/Kokona）插件框架（OneBot 11 协议）。
*   **数据来源**：Dakanu（https://www.dakanu.com/）公开战绩数据。
*   **触发方式**：群聊中**直接发送指定指令即可**（无需@机器人）。
*   **防误触机制**：框架采用精确前缀匹配，仅在识别到特定指令（如“看看”、“排行”、“帮助”）时才会响应。

---

## 二、 指令列表 (Commands)

| 指令 | 作用 | 参数 | 示例 |
| :--- | :--- | :--- | :--- |
| **帮助** | 查看插件使用说明及指令菜单 | 无 | `帮助` 或 `卡丘帮助` |
| **看看** | 查询玩家档案概览 | `<玩家昵称>` | `看看 米雪儿` |
| **看看对局** | 查询单场对局详情（支持短号查询） | `<玩家昵称> <对局号>` | `看看对局 米雪儿 114514` |
| **排行** | 查询排行榜 | `<页数(默认第1页)>` | `排行` 或 `排行 2` |

---

## 三、 功能详情与使用示例 (Examples)

### 0. 帮助菜单
*   **发送格式**：`帮助`
*   **返回数据**：返回排版整齐的文本菜单或渲染后的图片，列出所有指令的格式、参数说明及示例，引导用户正确使用。

### 1. 玩家概览查询
*   **发送格式**：`看看 <玩家昵称>`
*   **示例**：`看看 米雪儿`
*   **返回数据**：返回玩家的基本档案（头像、等级、当前段位、最高段位）、综合数据（总场次、胜率、KDA、场均伤害）以及最近对局简表。

### 2. 对局详情查询
*   **发送格式**：`看看对局 <玩家昵称> <对局号>`
*   **示例**：`看看对局 米雪儿 765895284264114514`
*   **返回数据**：返回指定对局的地图、比分结果、双方队伍人员的详细数据（击杀/死亡/助攻等）。

### 3. 排行榜查询
*   **发送格式**：`排行 [页数]`
*   **示例**：`排行` (默认第1页) 或 `排行 3` (查询第3页)
*   **返回数据**：返回全服玩家排行榜数据（支持 1-100 页，共 10,000 名玩家）。

## 四、 注意事项与交互规则 (Notes)

1.  **防误触与指令解析**：由于去除了 @ 机制，推荐在框架中设置严格的参数校验。例如，`看看` 指令后若未跟昵称参数，可静默处理或提示正确格式，避免群聊日常对话误触。
2.  **昵称与参数解析**：玩家昵称支持包含空格（框架需将指令后的所有剩余参数合并为昵称），但对局号必须放在最后一段。
3.  **短号匹配**：对局号支持短号查询（系统会自动提取尾数匹配最近对局）。
4.  **隐私保护**：若玩家在游戏内开启了隐私保护，接口仅能显示其基础档案（隐藏详细战绩）。
5.  **段位体系区分**：排位赛与挑战赛使用不同的段位计算方式，在数据渲染时需分开处理，避免混用。
6.  **高并发处理**：查询高峰期接口可能响应缓慢，需要等待几秒。所有网络请求需在异步线程池中执行，严禁阻塞 QQ 机器人的主事件线程。
7.  **异常处理**：如果长时间无回复，请检查机器人是否在线或联系管理员处理。

## 五、 开发者接口配置建议（Kokona & Dakanu 交互指南）

### 5.1 Kokona 框架集成说明
*   **插件入口**：使用框架的插件注解声明主类，并在 `onEnable()` 生命周期方法中集中注册命令。
*   **异步处理**：所有的 HTTP 网络请求和数据解析必须通过框架提供的异步任务工具（如 `TaskUtil`）执行，确保事件响应高效。
*   **消息构建**：使用框架内置的消息构建器（`MsgBuilder`）拼接文本、图片和富媒体消息，发送至群聊。

### 5.2 Dakanu 数据接口调用要点
*   **TLS/SNI 阻断绕过**：Dakanu 站点存在 TLS 握手阻断（直接请求域名会被 RST 重置）。在编写 HTTP 客户端时，**必须将连接目标改为 IP 地址，将 TLS 的 `serverName`（SNI）置空，并手动设置 `Host` 请求头为 `dakanu.com`，同时关闭证书校验**，否则所有请求都会失败。
*   **数据源映射**：Dakanu 接口按昵称或 UID 拉取数据，返回标准 JSON 结构。`看看` 功能解析概览数据，`看看对局` 可优先从概览返回的 `recent` 数组中提取对局详情。
*   **排行榜占位**：若 Dakanu 暂未公开排行榜独立端点，`排行` 功能可先以友好提示占位（如：“排行榜功能即将开放”），待接口明确后再扩展。
*   **数据缓存**：建议对玩家概览结果进行 60 秒左右的短期缓存，减少对 Dakanu 服务的请求压力，同时提升响应速度。
*   **安全提示**：该通道仅用于获取公开战绩数据，严禁通过此通道传输任何隐私数据或密钥。

### 6.2 关键实现决策

| 文档建议 | 实际实现 | 原因 |
| :--- | :--- | :--- |
| 用 `TaskUtil` 异步 | 自建 daemon 线程池 | 每条指令一个独立线程，异常不串扰，且不阻塞 QQ 事件线程 |
| 用 `HtmlToImageUtil` 出图 | **纯 Java2D 绘制** | 框架依赖 `wkhtmltoimage`（旧版 WebKit），现代玻璃拟态样式无法渲染，且系统未安装 |
| 排行榜先占位 | **已对接真实接口** | `/api/rankings` 已公开，支持 1-100 页 |
| 昵称单独请求 | `/api/search/players?q=` | 支持昵称、曾用名、UID 三种匹配方式 |

### 6.3 出图风格

所有机器人图片共用 `Theme` + `CardRenderer` 一套规范，与 `img/` 下的设计稿一致：

*   **底色**：粉紫 → 淡蓝的斜向渐变（`#FDF4F8` → `#F3F1FC` → `#ECF3FD`）
*   **卡片**：半透明白 + 1px 高光描边 + 柔和紫灰投影（玻璃拟态）
*   **分组条**：`#1A1B20` 深色圆角条 + 左侧橙色色标 + 右侧灰色附注
*   **强调色**：数值蓝 `#0284C7`、色标橙 `#FF7232`、胜利绿 `#059669`、失败红 `#E11D48`
*   **字体**：PingFang SC（中文）、DIN Alternate（数字），逐级回退
*   **版式**：1000px 定宽，高度按内容自适应

### 6.4 WebP 解码

Dakanu 的头像、立绘、地图、段位徽章全部是 WebP，JDK 自带 ImageIO 不支持。
插件把 TwelveMonkeys 解码器（5 个 jar）打包进 `src/main/resources/webp/`，
运行时解压到临时目录并用独立的 `URLClassLoader` 注册进 `IIORegistry`，
因此**使用者无需安装任何额外依赖**。解码失败会自动退化为无图占位，不影响文字出图。

### 6.9 出图性能

一次出图的耗时由三部分组成，已针对每一段做优化：

| 环节 | 优化前 | 优化后 | 做法 |
| :--- | ---: | ---: | :--- |
| 布局测量 | 28 s | 0 ms | 去掉“先画一遍再量高”，改为各视图精确计算 `layoutHeight()` |
| 图片获取 | 25 s | 3-4 s | 磁盘缓存 + 16 并发 + TLS 连接复用 |
| 绘制编码 | 0.2 s | 0.15 s | PNG 编码本就不慢，未改动 |

实测（`看看` 玩家概览，需 31 张唯一图片）：

| 场景 | 耗时 |
| :--- | ---: |
| 全新部署（磁盘缓存为空） | 4.7 s |
| 进程重启后（磁盘缓存命中） | 0.4 s |
| 同一玩家再次查询（内存缓存） | 0.11 s |

关键点：

1. **磁盘缓存**（`assets-cache/`）：头像、立绘、地图、段位徽章的内容都是固定的，
   路径即唯一标识，因此只需下载一次，进程重启后依然复用。
2. **并发预取**：每张图 5KB，但 TLS 握手约 1 秒，串行下载 31 张要 25 秒。
   实测 16 并发最优（8→8.8s，12→4.9s，16→3.8s，24→4.2s 开始回落）。
3. **连接复用**：按 `Content-Length` 精确读取响应体，从而支持 HTTP keep-alive，
   同一批图片复用已建立的 TLS 连接。
4. **缩略图**：头像缩到 192px、立绘 132px，避免大图反复缩放。

缓存目录可用 `font.install-missing` 同级的配置项管理，删除 `assets-cache/` 即可强制重新拉取。

### 6.10 素材缓存位置

下载过的头像、立绘、地图与段位徽章会落盘复用。按框架约定，插件配置目录为
`plugins/{插件名}/`（框架在 `setPluginInfo()` 中依据 `@KokonaPlugin(name=...)` 设置），
因此缓存目录为：

```
plugins/Celestia/assets-cache/
```

文件按原始站内路径扁平命名，便于辨认：

```
avatars_31001015.webp     # /avatars/31001015.webp
roles_celestia.webp       # /roles/celestia.webp
maps_map-01.webp          # /maps/map-01.webp
tiers_tier-7.png          # /tiers/tier-7.png
```

启动日志会打印实际路径：

```
素材缓存目录: /opt/kokona/plugins/Celestia/assets-cache
```

整个目录通常只有几 MB。删除即可强制下次重新拉取；
目录不可写时会自动退化为纯内存缓存，不影响功能。

### 6.11 空格可省略

框架的 `CommandManage.dispatch` 用 `content.split("\\s+")` 取第一个词作为命令名，
因此 `看看米雪儿` 会被当作一个整体命令名而匹配失败，只有 `看看 米雪儿` 生效。

插件通过 `QQListeners` 在事件阶段补回空格：命中已知指令前缀后，在指令名与参数之间插入一个分隔空格，
之后仍由框架统一执行（权限与作用域校验不变）。

| 输入 | 解析结果 |
| :--- | :--- |
| `看看米雪儿` | `看看` + `米雪儿` |
| `看看对局米雪儿114514` | `看看对局` + `米雪儿` + `114514` |
| `排行2` | `排行` + `2` |
| `排行榜` | `排行榜`（完整命令名，不拆） |
| `看看浅海梦是坏女人喵` | `看看` + `浅海梦是坏女人喵` |
| `今天天气不错` | 无匹配，不响应 |

两点注意：

1. **长名优先**：`看看对局` 先于 `看看` 匹配，避免多段指令被短名截断。
2. **对局号切分**：`看看对局` 后若以 3 位以上数字结尾，会自动再切一刀把对局号分离出来，
   避免整个 `米雪儿114514` 被当成昵称去查询。

监听器注册说明：框架只对「插件主类实例」扫描 `@QQEventHandler`，
因此 `QQListeners` 需要在 `onEnable()` 中通过 `QQEventManage.registerListener(...)` 手动注册。

### 6.12 同名玩家的候选选择

卡拉彼丘允许重名，例如「心心子」就存在两个不同的玩家（ID 6661532 与 6661504）。
若直接取搜索结果的第一个，用户会在无提示的情况下查到错误的人。

因此当**多个候选都精确匹配**时，机器人改为列出候选并等待用户回复序号：

```
找到 2 个与「心心子」匹配的引航者，请回复序号：
1. 心心子  ID 6661532  Lv.320
2. 心心子  ID 6661504
回复 1 - 2 选择，回复「取消」放弃（2 分钟内有效）。
```

判定规则：

| 情况 | 行为 |
| :--- | :--- |
| 只有 1 个候选 | 直接出图 |
| 多个候选但只有 1 个精确匹配（如「心夏」8 个候选） | 直接出图，用精确匹配的那个 |
| 多个候选且有多个精确匹配（如「心心子」） | 列候选等待选择 |

实现要点：

- 待选状态按「群号 + 用户号」隔离，多人同时查询不会串台，有效期 2 分钟。
- 序号只接受纯数字，避免误吞群里的正常聊天；「取消」可主动放弃。
- 选择后按原查询类型继续：`看看` 出概览图，`看看对局` 继续按对局号出对局图。
- 选择处理在框架线程池中执行，不阻塞事件线程。

### 6.13 WIKI 功能

接入 biligame 卡拉彼丘 WIKI（1007 个内容页面），提供两条指令：

| 指令 | 说明 | 示例 |
| :--- | :--- | :--- |
| `兑换码` | 列出可用兑换码，自动过滤失效项，按有效期分组 | `兑换码` |
| `wiki <关键词>` | 查询 WIKI 任意页面 | `wiki 信用分` |

`wiki` 支持全站 1000+ 页面，包括地图、勋章、喷漆、头像框、基板、
角色设定、剧情、活动、武器数据、玩法规则等。常见页面配有别名（`wiki 段位` 直达排位说明）。

#### 技术要点

1. **必须带 Referer**：站点启用腾讯 EdgeOne 防护，缺少 `Referer` 头时 API 返回 HTTP 567。
   带上站点自身的 Referer 即可正常访问。
2. **取 `prop=text` 而非 wikitext**：大量页面的数据来自 Lua 模块（`#invoke`）、Widget 或 SMW 查询，
   wikitext 里只有模板调用，渲染后的 HTML 才有实际内容。
3. **必须 `redirects=1`**：WIKI 有大量重定向页（如「好友亲密度」指向「好友」），
   不带该参数只会拿到“重定向到：”的提示。
4. **表格先扁平化**：`<td>` 之间常有换行，直接转文本会把一行表格拆散；
   先按 `<tr>` 切块、用 ` | ` 连接单元格，再转文本。
5. **目录过滤**：自动剔除「1 评级」「1.1 信誉评级」这类章节索引行。

缓存 30 分钟（WIKI 内容变动很慢），避免给上游造成压力。

### 6.16 BGM 点播

`BGM` 指令支持点播，曲目直链来自 WIKI（165 首，均在 `patchwiki.biligame.com`）。

| 用法 | 行为 |
| :--- | :--- |
| `BGM` | 出图列出全部曲目与序号（60 首/页，双列排版） |
| `BGM 5` | 按序号点播第 5 首 |
| `BGM 沐于春意` | 按曲名点播（支持模糊匹配） |
| `BGM 周年` | 未精确命中时列出相近曲目供选择 |

#### 发送方式

`config.yml` 中 `bgm.send-mode` 控制：

| 值 | 行为 |
| :--- | :--- |
| `record`（默认） | 发送语音消息，失败时自动补发直链 |
| `link` | 只发曲名与直链，由用户自行播放 |

**为什么需要两种模式**：QQ 语音消息对时长与格式有硬限制（多数实现限制 60 秒内，
部分客户端还要求 silk/amr），而 WIKI 上的曲目普遍 2-5 分钟、约 5 MB，
直接以语音发送很可能被客户端拒绝或降级成文件。
若你的 OneBot 实现支持长音频，用默认的 `record` 即可；否则建议设为 `link`。

点播时把直链交给 OneBot 的 `record` 消息，由客户端自行拉取，不占用机器人带宽与磁盘。
### 6.17 多级菜单

`帮助` 不再是一张平铺的指令清单，而是可导航的多级菜单：

```
功能菜单（L1）
├── 战绩查询        → 玩家概览 / 对局详情 / 排行榜
├── 游戏资料        → 角色 / 武器 / 地图 / 模式 / 信用分
├── 装饰图鉴        → 勋章 / 喷漆 / 头像框 / 基板 / 名片 / 核心
├── 游戏延伸        → BGM / 壁纸 / 表情包 / 漫画 / 联动 / 周边
├── 福利与活动      → 兑换码 / 活动 / 赛季
└── 使用说明        → 完整指令一览
```

继续向下是 **WIKI 页面章节（L3）** 与 **超长章节分页（L4）**：

```
装饰图鉴 → 勋章（18 个章节）
  1  概览            4 行
  2  排位段位奖励勋章      680 行  → 再分 4 段
  3  宿舍誓约奖励勋章      36 行
```

#### 交互方式

| 输入 | 行为 |
| :--- | :--- |
| `帮助` | 打开菜单（根层级） |
| 序号 | 进入下一层 |
| `返回` / `0` | 回到上一层 |
| `取消` / `退出` | 关闭菜单 |

每层出图都带面包屑（`功能菜单 › 装饰图鉴 › 勋章`），用户始终知道自己在哪一级。

#### 为什么需要多级

WIKI 的图鉴页极长：表情包 1431 行、基板 2295 行、勋章 1558 行。
直接整页出图会被截断（上限 160 行），用户找不到想要的内容。
菜单按 h2/h3/h4 标题切出章节，超过 200 行的章节再自动分页（每段约一张图），
这样任意页面都能被逐层展开到可读的粒度。

菜单状态按「群号 + 用户号」隔离，3 分钟无操作自动失效；
菜单只消费序号 / 返回 / 取消，其余输入仍走普通指令，不会吞掉正常聊天。
### 6.18 图鉴网格（WIKI 内容下钻到条目）

装饰图鉴类页面（头像框 / 勋章 / 喷漆 / 基板）本质是「一堆带图的条目」，
按章节看文字没有意义。菜单会自动识别这类页面并切换到 **图标网格模式**：

| 页面 | 条目数 | 分页 |
| :--- | ---: | ---: |
| 头像框 | 71 | 2 页 |
| 勋章 | 352 | 10 页 |
| 喷漆 | 670 | 19 页 |

每页 36 个条目（6 列 × 6 行），直接画出实物缩略图 + 序号 + 名称，
用户看到图再按序号点开，而不是在一张 4500px 的长图里翻文字。

#### 解析方式

从 `div.gallerygrid-item` 提取每个条目的：

- **名称** —— `span.badge` 的文字（如「闪耀鎏金」）
- **图片** —— `img[src]` 的地址

加载时按 URL 的 host 建连（图片在 `patchwiki.biligame.com`，与 WIKI 主站不同域），
- 60 个条目的缩略图并行预取，冷启动约 0.85 秒。
### 6.19 序号的使用规则

出图上的序号只在**真的可以回复点选**时才显示，避免误导：

| 卡片 | 是否显示序号 | 原因 |
| :--- | :--- | :--- |
| 菜单（MenuCard） | ✅ 显示 | 回复序号可进入下一层 |
| BGM 曲目（BgmCard） | ✅ 显示 | 回复「BGM 序号」可点播 |
| 图鉴网格（GalleryCard） | ❌ 不显示 | 条目动辄数百个，回复数字只会切换分页 |
| 章节内容（WikiCard） | ❌ 不显示 | 纯阅读内容 |
| 兑换码（RedeemCard） | ❌ 不显示 | 纯阅读内容 |

图鉴的分页由**上一层菜单**控制：回复「返回」回到分页列表，再选页码。
因此在图鉴图上标序号没有意义，只会让用户尝试回复后得到「序号超出范围」。
### 6.20 直接指令（不经过菜单）

菜单用于「不知道有什么」时的探索；已知要查什么时，每条内容都有直达指令。
菜单能到达的 20 个页面全部注册了独立指令，两者行为一致。

#### 图鉴页（参数为页码）

| 指令 | 条目数 | 分页 |
| :--- | ---: | ---: |
| `勋章` | 352 | 10 页 |
| `喷漆` | 670 | 19 页 |
| `头像框` | 71 | 2 页 |
| `基板` | — | — |
| `个性名片` / `核心` | — | — |

用法：`勋章` 出第 1 页，`勋章 2` 出第 2 页。

#### 文字页（参数为章节序号）

| 指令 | 说明 |
| :--- | :--- |
| `地图` / `角色` / `武器` | 不带参数列章节，`地图 2` 看第 2 章 |
| `信用分` / `核心` / `活动` / `赛季` | 玩法与规则 |
| `战斗模式` / `角色定位` / `武器数据` | 规则与数值 |
| `壁纸` / `表情包` / `四格漫画` / `联动` / `周边` | 游戏延伸 |

两种入口的关系：

```
发送「帮助」  → 逐层浏览 → 找到内容
发送「勋章」  → 直达        → 同样的内容
```

指令名均可在 `config.yml` 的 `command.*` 下修改。
### 6.21 两个入口：帮助 与 菜单

| 指令 | 作用 | 适用场景 |
| :--- | :--- | :--- |
| `帮助` | 出静态的**全部指令一览** | 想知道有哪些指令、怎么用 |
| `菜单` | 打开**可逐层浏览的功能菜单** | 不知道内容在哪，需要翻着找 |

两者的区别：

```
帮助  → 一张图，列出所有指令与示例（看完即止）
菜单  → 可导航：分类 → 页面 → 章节 → 内容
```

菜单根层的页脚会提示「回复「帮助」查看全部指令」，帮助图的副标题也会提示「发送「菜单」可逐层浏览」，
两个入口互相指路。

> 早先版本把 `帮助` 直接绑到了菜单，导致「想看指令列表」和「想翻内容」混在一起。
> 现在拆开：`帮助` 保持静态一览的轻量语义，导航交给 `菜单`。
### 6.22 指令精简：三项改为仅菜单可用

`四格漫画`、`联动`、`相关周边` 不再提供独立指令，只能通过 `菜单` 进入：

```
菜单 → 4 游戏延伸 → 四格漫画 / 联动 / 相关周边
```

这样做的原因：这三项更新频率低、使用频次也低，
注册成顶层指令会挤占指令一览，让高频功能（战绩、图鉴）被稀释。

仍然可以通过 `wiki <页面名>` 查到（这是通用查询能力，不受影响），
例如 `wiki 官方四格漫画`。
